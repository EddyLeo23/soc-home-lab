## Summary

Seven failed interactive logons against the local standard account labtest within 20 seconds triggered the
rule, which alerts on 5 or more failures per account and host in a 10-minute sliding window. This was a
deliberate runas test on my own machine. It validates the detection logic against a controlled sequence of
failed interactive logons; it does not establish coverage for network logons, RDP, password spraying or
attacks against other hosts. The report is written as if the activity were real, to show the investigation
steps and what the evidence supports.

## Windows event notes

- 4625 (an account failed to log on): recorded on the machine where the logon was attempted. Subject is the
  account that requested the logon; the target account is the one that failed. In the Wazuh copy of the raw
  event from an earlier burst, the Subject was the invoking local user and the caller process was svchost.exe.
  The raw 4625 of the 17:04 burst was not inspected.
- Status 0xC000006D with SubStatus 0xC000006A: 006D is the generic "unknown user name or bad password" status;
  the SubStatus refines it, and 006A means a wrong password for a user name that exists. A status code reports
  the system's view of one attempt, not the identity or intent of whoever made it.
- LogonType 2 and seclogo: type 2 is interactive. runas uses the Secondary Logon service, which appears as
  logon process seclogo, so seclogo with type 2 and a loopback address fits a runas-style local attempt. A
  lock-screen typo is also type 2 but uses User32. Neither value alone proves the origin.
- 4688 (a new process was created): with command-line auditing on (it is on this host) it records the command
  line and the creating account. Linking it to the failures relies on timing, the target account in the command
  line and, where available, matching logon IDs. The logon-ID match was not performed.
- 4740 (an account was locked out): its absence means no lockout event was observed in the collected data. It
  is consistent with 7 failures below a threshold of 10 and with 4740 collection being configured in the data
  collection rule.

## Recommended actions if this were a real incident

1. Validate: confirm whether the activity was authorized and identify the initiating account and process.
2. Scope: check for successful logons, other targeted accounts, and similar activity on other hosts.

       SecurityEvent
       | where TimeGenerated > ago(24h)
       | where EventID == 4625
       | summarize Failures = count(), Accounts = dcount(TargetUserName) by Computer, IpAddress

       SecurityEvent
       | where TimeGenerated > ago(24h)
       | where EventID == 4624 and TargetUserName =~ "<account>"
       | project TimeGenerated, Computer, LogonType, IpAddress, LogonProcessName

3. Preserve: retain the relevant authentication events, process-creation records, timestamps and raw alert
   evidence.
4. Escalate proportionately: if the activity remains unexplained, follow organizational procedures for account
   protection, credential resets or endpoint containment as warranted. Escalate sooner if a success follows the
   failures, a privileged account is targeted, one source hits several accounts or hosts, or the logon type is
   3 or 10 with an external source.

These are hypothetical response steps. No containment action was required for this authorized lab test.

## Detection engineering

| Setting | Value |
|---|---|
| Threshold | 5 or more failed logons (all logon types, all failure sub-statuses) |
| Window | 10-minute sliding window in 1-minute steps |
| Grouping | Per Computer + TargetUserName; one alert per result row |
| Schedule / lookback | Every 10 minutes, 1 hour lookback |
| Duplicate suppression | Only events ingested in the last 10 minutes can alert |

Blind spots (design-level; most untested):
- Low-and-slow attempts below 5 per account per 10 minutes.
- Password spraying (one or two attempts per account across many accounts), because counting is per account.
- Attacks spread across hosts, because grouping is per host (one host in this lab).
- The source address is not part of the grouping, so failures from different sources count together.
- Only hosts that send 4625 events are covered.
- Events whose ingestion falls outside the 10-minute new-data window, for example after a skipped or very
  late rule run, would not alert.
- Benign typos by the owner could reach the threshold; not observed.
- Network and RDP failed logons were not tested.

### v0.4 stretch item - alert context and rendering

Not implemented in v0.3.

- Surface the initiating Subject account in the alert's investigation context. The v0.3 query does not carry the
  Subject columns through its summarize steps, so they must be added first. Verify the rule's output schema
  before assuming the Subject can be mapped as an entity; if it cannot be mapped cleanly, show it in custom
  details instead. In this lab the Subject is the real local username, so incident screenshots would need
  redaction before publication.
- Render the failure-type array as readable values (for example with strcat_array) in the alert description,
  not as raw serialized data.
- Validate both changes against the raw Windows events and the resulting Sentinel incident.

Acceptance criteria: the initiating account is visible in the intended alert field, the failure-type values
render correctly, and a controlled repeat confirms that the changes do not break detection or introduce
duplicate incidents.

Other ideas, not scheduled: add the source address as a custom detail (and as an IP entity when it is not
loopback); a companion rule for failures followed by a success; a password-spraying rule; tests for network and
RDP failed logons.
